图形学不是一开始就要背一堆公式。对游戏开发者来说，更实用的入口是先回答一个问题：屏幕上的一个像素，到底经历了哪些工程步骤才出现？

如果你能把这个链路说清楚，再去看 Shader、渲染管线、性能优化和 Frame Debugger，很多概念就会从“玄学参数”变成“可观察的状态变化”。

## 基础心智模型

一次常见的实时渲染可以粗略拆成这些阶段：

1. CPU 准备场景数据、剔除对象、提交绘制命令。
2. GPU 读取顶点数据，执行顶点着色器，把模型空间坐标变换到裁剪空间。
3. 光栅化阶段把三角形转成屏幕片元。
4. 片元着色器计算颜色、采样纹理、处理光照或材质。
5. 深度测试、混合、模板测试等状态决定片元是否写入目标缓冲。
6. 后处理和最终合成把画面输出到屏幕。

这个流程不一定覆盖所有管线细节，但足够作为入门骨架。

## 顶点不是模型，片元也不是像素

很多初学问题来自概念混用。

顶点是几何数据的基本输入，它通常包含位置、法线、切线、UV、顶点色等属性。模型是由顶点、索引、材质、骨骼、贴图和运行时状态共同组成的资源。

片元是光栅化产生的候选像素。它还需要经过深度、模板、混合等测试，才可能真正写入颜色缓冲。因此片元着色器运行次数可能远高于最终可见像素数量。

这也是为什么 Overdraw 会吃性能：你看见一个像素，GPU 可能已经为它计算过很多次。

## 纹理采样不是“读取图片”那么简单

纹理在 GPU 中更像一组被优化过的采样数据。采样时会涉及：

- 采样坐标，也就是 UV。
- 过滤方式，例如 Point、Bilinear、Trilinear。
- Mipmap，用更小的纹理层级减少远处闪烁和带宽压力。
- Wrap Mode，决定 UV 超出 0 到 1 后如何处理。
- 颜色空间，例如 Linear 和 Gamma。

在 Unity 中，很多画面问题其实不是 Shader 写错，而是贴图导入设置、颜色空间或 Mipmap 策略不匹配。

## 渲染状态决定“能不能写进去”

Shader 输出颜色只是中间结果。最后能否进入屏幕，还要看渲染状态：

```txt
ZTest     深度比较规则
ZWrite    是否写入深度
Blend     如何和已有颜色混合
Cull      剔除正面、背面或不剔除
Stencil   模板测试与写入
Queue     渲染队列顺序
```

透明物体排序、UI 穿插、描边遮挡、特效过曝、阴影异常，经常都和这些状态有关。

## Unity 开发者的学习顺序

建议按这个顺序建立知识网络：

1. 坐标空间：Object、World、View、Clip、Screen。
2. 基础 Shader：顶点到片元，UV 到贴图采样。
3. 深度与混合：理解不透明、透明、Alpha Test。
4. 光照模型：从 Lambert、Blinn-Phong 到 PBR。
5. 渲染管线：Built-in、URP、HDRP 的职责差异。
6. 调试工具：Frame Debugger、RenderDoc、Profiler。

## 关键结论

图形学入门的重点不是一次性理解所有数学，而是建立可调试的工程模型。你需要知道一个渲染结果来自哪些输入、经过哪些阶段、受哪些状态影响。

当你能把“看起来不对”拆成“几何、材质、纹理、光照、渲染顺序、后处理、平台差异”这些可验证方向时，图形学就真正开始服务于游戏开发。
