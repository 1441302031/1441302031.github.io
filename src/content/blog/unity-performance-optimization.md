性能优化不是把所有代码都改快，也不是看到 GC 就立刻重构。真正有效的优化要从目标和指标开始：目标平台是什么，帧率预算是多少，瓶颈在哪里，改动会牺牲什么。

没有指标的优化，通常只是把复杂度从一个地方搬到另一个地方。

## 先定预算

帧率目标决定每帧预算：

```txt
30 FPS 约等于 33.33 ms / frame
60 FPS 约等于 16.67 ms / frame
120 FPS 约等于 8.33 ms / frame
```

移动端小游戏常见目标是稳定 30 或 60 FPS。不要只看平均帧率，还要关注 P95、P99、卡顿峰值、加载等待和内存峰值。

## 先判断瓶颈类型

常见瓶颈可以分成几类：

- CPU：脚本逻辑、物理、动画、UI、渲染提交。
- GPU：片元、Overdraw、后处理、阴影、带宽。
- 内存：贴图、网格、音频、对象常驻、缓存策略。
- 加载：资源 IO、反序列化、Shader 变体、场景切换。
- GC：短生命周期分配、装箱、字符串、临时集合。

优化前先用 Profiler、Frame Debugger、Memory Profiler 或平台工具确认是哪一类。

## CPU 优化方向

CPU 侧重点是减少不必要的每帧工作。

高频检查项：

- `Update` 中是否有可降频逻辑。
- 是否频繁 `GetComponent`、查找对象、字符串拼接。
- UI 是否因为数据刷新导致整棵布局重建。
- 动画、物理、粒子是否在不可见状态继续运行。
- 对象池是否减少了频繁创建销毁。

不要把所有逻辑都塞进对象池。对象池适合创建成本高、生命周期短、数量频繁波动的对象，不适合无限缓存。

## GPU 优化方向

GPU 侧先看像素成本，再看几何和状态切换。

移动端尤其要关注：

- 半透明特效造成的 Overdraw。
- 大面积 UI 和模糊背景。
- 高分辨率贴图和过多采样。
- 实时阴影和多光源。
- 后处理链路。
- 不必要的 Render Texture。

如果画面简单但 GPU 时间高，优先检查 Overdraw、后处理和渲染分辨率。如果 Draw Call 高但 GPU 不慢，问题可能在 CPU 提交侧。

## 内存和资源优化

内存优化不能只看资源大小，还要看运行时常驻和峰值。

常见策略：

- 按平台设置贴图压缩格式。
- 控制最大贴图尺寸和 Mipmap。
- 拆分常驻资源与按需资源。
- 管理 Addressables 或 AssetBundle 生命周期。
- 避免场景切换时短时间双份资源同时存在。
- 对 Shader Variant 做裁剪和预热。

小游戏环境里，包体、首屏加载和运行内存往往比纯帧率更敏感。

## 优化闭环

一次可靠的优化应该形成闭环：

1. 记录问题：平台、机型、场景、复现路径、指标。
2. 定位瓶颈：Profiler 截图或采样数据。
3. 提出假设：为什么慢，慢在哪里。
4. 小步修改：只改一个方向。
5. 对比数据：修改前后同条件测试。
6. 记录结论：收益、代价、适用范围。

## 工程结论

Unity 性能优化的核心不是技巧清单，而是排查纪律。先定位，再行动；先数据，再取舍。

当你能把“卡”描述成“某场景在某机型 P95 帧耗从 18ms 升到 32ms，GPU 片元开销来自半透明特效 Overdraw”，优化就已经成功了一半。
